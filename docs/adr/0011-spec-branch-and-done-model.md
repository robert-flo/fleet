# Spec branch and done model

Decided 2026-10-01. Complements ADR 0010 and robert-flo/Template `AGENTS.md` and `RELEASE_POLICY.md`, which stay the source of truth for worktrees, rebase, PRs, CI and cleanup; this ADR only fixes which branch is each branch's base and when work counts as done.

- **The PM owns specs end to end**, several at once. Engineering requests keep the fixed flow grill-with-docs, then to-spec, then to-tickets, with nothing skipped (`ask-matt` only when stuck). The PM never changes code; workers do.
- **The spec is a GitHub issue.** The issue published by to-spec is the shared map for every worker on it (several, possibly of different roles). to-tickets splits it into GitHub sub-issues. Both the spec issue and its sub-issues carry `ready-for-agent` (label per Template `docs/agents/triage-labels.md`; the to-spec and to-tickets defaults, skills unmodified). A worker running `/implement-spec` takes the spec issue and works the sub-issue task graph on the spec branch, its integration branch; a worker running `/implement` takes one sub-issue.
- **to-tickets is always mandatory** for Engineering, even when the work fits in one session (at least one sub-issue). This intentionally overrides the Template `AGENTS.md` decision-tree branch that goes from to-spec straight to implement.
- **Triage.** The PM runs `/triage` only on issues it did not create (incoming or raw ones, e.g. opened by Roberto by hand). Tickets from to-tickets are already agent-ready and are never re-triaged.
- **Spec branch.** When the spec issue is published, the PM creates its branch with `git-issue-worktree` on the spec issue, base = the repo's default branch (`main` for reel), and pushes it. The name comes from the helper (issue number + slug, base recorded); it is never invented. The PM does not commit to it.
- **Worker branches.** Each worker creates its branch with `git-issue-worktree` on its sub-issue, base = the spec branch (as many branches as it needs; chores use `git-create-worktree`; never raw `git worktree`). It rebases onto its base and pushes with `--force-with-lease` (never merges the base into the topic), gets CI green and runs `/code-review`, then merges its own PR into the spec branch when everything passes. Temporary branches and worktrees are deleted only after the merge is confirmed, per `RELEASE_POLICY.md`.
- **Final PR.** When every sub-issue is merged into the spec branch, the PM opens the PR from the spec branch to the default branch. It is the only PR of the spec that Roberto approves, and he merges it. The default branch still never gets direct commits.
- **Trivial.** One `ready-for-agent` issue, no grill and no spec. The worker branches with `git-issue-worktree` from the default branch, runs implement then code-review, and opens its PR to the default branch for Roberto to merge.
- **TickTick.** One task per spec, moving through the six ADR 0007 columns; columns stay states (no column per spec). Each sub-issue is a subtask (checklist item), checked off when its PR merges into the spec branch. A trivial is one issue and one task. With every subtask checked, the task moves to 🌼 QA TO CONFIRM and the PM opens the final PR.
- **Done.** A spec is done when all its sub-issues are complete and its PR to the default branch is ready to merge; a trivial, when its PR is ready to merge. The task moves to 🌼 DONE only when Roberto merges, after the PM confirms the merge on GitHub; the PM then removes the spec branch and worktree.
- **Worker side**: see ADR 0012 and `templates/worker.md`.
